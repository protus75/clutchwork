The driver plan (docs/roadmap-driver-plan.md section 6 step 1) says serve's idle point should supervise every unsupervised Reject-queue stem before new work. The merged driver-loop and supervisor-rework code supervises only inside runner.drive. A stem that reaches the queue another way is never machine-supervised: a merge-queue failure routed through serve's consume_result, or a drain quiescence reject_arrival. It waits for the supervising agent loop to release it with clutch prompt diagnose.

The gap against the design is real, but it does not yet meet the bar of a materially harmful behavior gap that fits in one ticket. (1) No stem is stuck waiting for a person. The merged drain-loop prompt already has the supervising agent loop release these stems through clutch prompt diagnose, and the message says so. (2) It happens rarely: 7 of 190 routed terminals came from the merge stage, plus 1 reject_arrival. (3) The design is not settled. The message itself says an idle-point supervisor needs its own worktree and fresh Effect keys outside drive, and nothing defines either yet. A ticket written now would have to make those design choices, so it is not a bounded repair. Reopen this if a merge-stage or quiescence Reject-queue arrival sits unreleased while the supervising agent loop is running, or if the share of non-drive arrivals grows enough that agent-loop releases become a recurring cost. Also reopen it once the plan states how idle-point supervision gets its worktree and how its Effect keys are formed.
