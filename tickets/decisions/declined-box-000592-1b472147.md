The open evidence-envelope ticket plans to add capture steps (git rev-parse/tree id, evidence store write, prune) inside the provider call. Thresh.run in clutch/thresh.py records any exception that is not a ProviderCallError as failure class 'unclassified', and _COUNTED includes that class. Once the envelope merges, a fault in clutch's own capture could count against a healthy provider's breaker, or turn a successful, already-billed call into a failure. The envelope ticket has no criterion that keeps capture faults out of provider failure accounting.

The risk is real but does not exist yet. On current main no capture step runs inside ProviderLLM.admitted_call's operation; the steps described exist only in the unmerged tickets/evidence-envelope/ticket.md. The fallback is real: clutch/thresh.py:247 maps any non-ProviderCallError to 'unclassified', and clutch/thresh.py:26 puts 'unclassified' in _COUNTED. Still, no run has shown a capture fault opening a breaker or discarding a result. A separate ticket now would also have to depend on evidence-envelope and edit the same files. The cheaper fix is a scope change to the open evidence-envelope ticket before it runs: a pre-spawn capture failure raises a setup-class error that is not counted against the provider, and a post-call capture write failure is logged to engine.log and leaves the call's result unchanged. That scope change is the operator's decision, not triage's. Record box-000588, which flagged a post-merge gap in the same ticket, was declined for the same reason. Reopen if evidence-envelope merges without this guard and a run shows a capture-path GitError or OSError recorded as 'unclassified' in a thresh outcome, a breaker opening, or a successful call's result being lost.
