When a published Rework split retires its parent, failure_terminal calls reject_ticket (clutch/runner.py:437), and reject_ticket always writes reject_verdict verdict=kill actor=operator (runner.py:613). The journal therefore says an operator issued a kill that no operator issued. The note counts 3 of the journal's 32 operator kills as machine-issued and says doc counts of operator verdicts are too high because of them.

The mislabel is real, but it does not change any runtime behavior. Every engine reader that checks actor on reject_verdict looks only at keep verdicts: caps.py:28 (lineage reset), drain.py:83, runner.py:591 and observe.py:243. stats.py:170 counts actors for keeps only. status.py and apply_admission use reject_verdict without checking actor. No cap, hold, dispatch, menu or stats figure is computed from the kill actor. What goes wrong is offline analysis that reads the journal by hand, such as the 28-kill figure in docs/roadmap-driver-plan.md. That is a record-accuracy and plan-wording problem with no reachable incorrect runtime behavior, so it is below the admission bar. Reopen if a runtime consumer (stats, scorecard, retro, the baseline/verdict-human-only binding, or a verdict-rate gate) starts reading reject_verdict kill actor, or if a superseded parent state is adopted for split retirement.

- clutch/runner.py:435-437 failure_terminal calls reject_ticket(ticket.stem, checkout) when split is true
- clutch/runner.py:613 reject_ticket appends reject_verdict verdict=kill actor=operator unconditionally
- clutch/caps.py:28, clutch/drain.py:81-83, clutch/runner.py:591, clutch/observe.py:243 read actor only for verdict=keep
- clutch/stats.py:170 counts actors only for keep verdicts; no kill-actor counter exists
- clutch/status.py:53 and :207 and clutch/runner.py:707 use reject_verdict without checking actor
