2. Mechanism (clutch/serve.py `merge`, lines 506-536 at HEAD 1c748cea): the merge poll does
       if not self.merge_work(): return
       async with self.mutations():
           self.control.poll()
           ...

   `merge_work()` (serve.py 476-) returns True for an accepted, not yet completed confirm or reject decision. `mutations()` is `admission.exclusive()` (clutch/daemon.py 596-601), which waits until no run holds a slot (`_holding == 0`) and, while it waits, makes `_acquire_run` refuse new runs. So a verdict waits for every running implementation and blocks admission while it waits.

3. Why that exclusivity is wider than needed: `apply_verdict` -> `runner.apply_admission` (clutch/runner.py 803-848) commits the ticket-plane change to the main checkout (`c.git.commit(c.repo, "clutch(<stem>): confirmed", only=[ticket path])`) and appends journal signals. That must not overlap the merge queue's squash and delivery, which also commit to main. It does not touch any implementation: an implementation runs in its own worktree.

Cost: with an operator confirming tickets every few minutes, max_runs 2 behaves like 1 for much of the time.
