## Goal / Why
Roadmap row 199, the last call site of rows 179, 192 and 193: Triage is the only surface that accepts a `majority-verdict` panel in config (`PANEL_SURFACES["majority-verdict"]` already lists `triage`, so `clutch/config.py` needs no edit) and then ignores it. After this ticket a routing row `{tier, surface: triage, panel: {size: N, combine: majority-verdict}}` makes `_settle_pass` run N member triage calls through `Driver.run_panel` for each pending message and settle it from the majority verdict. Merged and reused, not redone: `clutch/stages.py::_panel_combine(panel, selected)` (returns `(replies, members, cost)`), `clutch/panel.py::majority_verdict` with the total `TRIAGE_ORDER = ("declined", "tombstone", "author")`, `PanelResult`, `providers.panel_members`, and the `neighbors` block value `_settle_pass` builds once per message.

Read from the merged `_settle_pass`: the one `driver.run(LlmStage(surface="triage", emits=TriageReply, gates=[], render=render_message), message, ticket=None, run_seq=message.seq, attempt=pass_no, workspace=checkout.repo, tier=checkout.config.routing_default_tier, effort=spec.meta.effort, stuck_budget=TRIAGE_STUCK_S, expected_budget="surface", scope_fence=())` call; a result whose `outcome != "ok"` gives the line `"<id>: <outcome>; remains pending"` and records, journals and files nothing (it never reads `result.findings`); an `ok` result's `artifact` is a `TriageReply` (`verdict`, `link`, `summary`, `rationale`, `evidence`, `reopen_after_days`, validated by `TriageReply._coherent`). Verdicts are final and drive what the engine files: `author` records `Verdict(... rationale=reply.rationale)` and invokes `author(...)`; `declined` and `tombstone` write a decision record through `_record` from `reply.summary`, `rationale`, `evidence`, `reopen_after_days` and (tombstone) `link`.

Design of the change in `_settle_pass`, after `neighbors = await neighbors_block(...)` and `inputs` (both built once per message; every member's calls and re-prompts render from the same `inputs`, so `neighbors_block` is awaited once per message, never once per member):
- Size is `len(panel_members(checkout.config, checkout.config.routing_default_tier, "triage"))`; `ProviderSetupError` means size 1. For a config with no `triage` row `panel_members` resolves the `review` row, whose `Route.surface` is not `triage`, so the size is 1.
- The keyword arguments above are built once in one dict `kwargs`. Size 1 calls `driver.run(stage, message, **kwargs)`; size 2 or 3 calls `driver.run_panel(stage, message, size=size, **kwargs)`. No `kind` is passed (triage passes none today).
- Size 2 or 3: if `panel.members` is empty (every member `infra_error`, or the stuck budget ran out before any member finished) the result is `StageResult("infra_error", None, [], Cost())`; else the first member whose outcome is not `ok` (a `timeout`, `invalid_artifact`, a `ProviderDroughtResult`) is the result; else `replies, members, _ = _panel_combine(panel, selected)`, every reply is a `TriageReply`, `reply, facts = majority_verdict(replies, TRIAGE_ORDER, members, panel.dropped)`, the result is `StageResult("ok", reply, [], Cost())` and one engine-log event is written: `driver.log.event("panel_facts", box_id=message.id, attempt=pass_no, surface="triage", **facts.model_dump())` (the log, never the journal). The code after the call (the `outcome != "ok"` line, the `reopen` rewrite, the `author`, `tombstone` and `declined` branches) is unchanged and runs once on `result`. Triage reads no `cost`, so the member cost `_panel_combine` returns is unused. Rejected simpler approach: none smaller exists; copying `_panel_combine`'s lines would make a fourth copy of the member bookkeeping.

How the combined reply is built (exactly): the combined `TriageReply` is one member's whole reply, never a mix of fields. It is the first reply, in member order, whose `verdict` equals the winning verdict (`majority_verdict` returns it); `verdict`, `link`, `summary`, `rationale`, `evidence` and `reopen_after_days` all come from that one member, so `TriageReply._coherent` holds as it did for the member and no field is synthesized, merged or re-validated by new code. The combined `author` verdict carries no ticket proposal: `TriageReply` has no ticket field, and the ticket text is written by the later `author(...)` call, which is unchanged and is called once per message (a panel never multiplies Author calls). Only `reply.rationale` of the winning member goes into `Verdict(... rationale=...)`.

Outcomes, each by name (ties are decided by `TRIAGE_ORDER`, `declined` before `tombstone` before `author`, so a tie never authors):
- **Unset panel**: no `Route.panel`, or `size: 1`: one `driver.run`, zero `run_panel`, the call and its keyword arguments, the effect key `llm/triage/<seq>/triage/<pass>/<call>`, the spool, the journal events, the decision records and the returned lines exactly as today, no `panel_facts` event.
- **Majority**: the verdict most surviving members gave. Worked example, size 3 (candidates `codex`/`a` repeated, one-candidate row), m0 `declined` (summary `S0`, rationale `R0`, evidence `["e0"]`, `reopen_after_days` 14), m1 `author` (summary `S1`, rationale `R1`), m2 `declined` (summary `S2`, rationale `R2`, evidence `["e2"]`, `reopen_after_days` 30): `declined` has two votes, so the reply is m0's whole reply; the record `declined-<id>` is written with summary `S0`, rationale `R0`, evidence `["e0"]`, `reopen_after_days` 14, and no Author call is made; m2's text and 30 days are not used and m1's author vote files nothing. A second example: `author`, `author`, `tombstone` gives `author` with m0's rationale in `Verdict` and one `author(...)` call.
- **Tie**: `declined` vs `author` (size 2) gives `declined`, with m1's reply if m1 is the `declined` member; `author`, `tombstone`, `declined` (a size-3 three-way tie) gives `declined`, with m2's reply; `author` vs `tombstone` gives `tombstone` with its member's `link`; a tie never produces `author`.
- **Never weaker evidence than a single call**: a combined verdict is reached by at least as many independent surviving votes as the single call's one (except when members are dropped for `infra_error`, or when the shared stuck budget ends the panel early, in which case Triage votes on the members that finished, exactly as `diagnose` does), and any tie falls to the verdict that files less work (`author` needs a strict plurality of the surviving members, because it loses every tie). A panel left with one surviving member (size 2 with one dropped) settles exactly as that member's single call would. A non-`ok` outcome of any member leaves the message pending with nothing filed even if the others agree, so a panel never files on fewer completed members than it asked for except through `infra_error` drops. The existing guards run on the combined reply as on a single one: with `message.reopen` a `tombstone` becomes `author` as today (applied after the vote, to the winning reply), and a `tombstone` whose `link` names no merged or committed non-rejected ticket or committed decision record becomes `declined` with the `unresolvable link` evidence. When winning `tombstone` members name different links the first winner's link is used and that same guard validates it; example: m0 `tombstone` link `a`, m1 `tombstone` link `b`, m2 `declined`: the vote is `tombstone`, the reply is m0's with link `a`. Rejected simpler approach to this one rule: demoting disagreeing links to `declined` would add a second decision path with no incident behind it.
- **Member failing**: a member whose call fails with `infra_error` is in `PanelResult.dropped`; the survivors are voted and `panel_facts.dropped` records `{index, failure_class: "infra_error"}` with the original member index.
- **All members failing, or the stuck budget exhausted before any member finished**: `panel.members` is empty; the line is `"<id>: infra_error; remains pending"`, which is what size 1 writes for an `infra_error` result; no record, verdict or `panel_facts`. `PanelResult.dropped_findings` (for example a `quota_exhausted` finding of a dropped member) is deliberately not read, exactly as `_settle_pass` never reads `result.findings` of a failed single call; a test proves the returned line is identical with and without it.
- **Member not ok**: the first non-`ok` member's outcome gives `"<id>: <outcome>; remains pending"`, nothing filed, no `panel_facts` (`ProviderDroughtResult` included).

Why this is the smallest slice: one function body in `clutch/triage.py`, one unit test file, one integration source check and two stub-config lines in existing tests, two doc sentences. It fits 50 stuck minutes, so no split is needed.

## Definition of rejected
